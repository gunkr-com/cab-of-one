# 위협 모델

[English](threat-model.md) | **한국어**

> 초안. 이 문서는 현재 코드와 문서화된 Claude Code 동작을 설명합니다. **측정되지 않음**으로 표시된 항목은 실제 Claude Code 세션에서 관찰된 적이 없습니다. 이 문서는 [threat-model.md](threat-model.md)의 한국어판입니다.

## 무엇을 위한 것인가

cab-of-one은 적대적이기보다 부주의한 에이전트를 상정해 만들었습니다.

- 실수를 합니다.
- 지시를 지나치게 넓게 해석합니다.
- 종료 코드나 "Success" 줄을 믿습니다.
- 긴 세션 도중에 절차를 잊습니다.

절차를 따르는 것을 잊는 사람도 다룹니다.

다음은 막지 **못합니다**.

- 의도적으로 통제를 피해 가는 에이전트. 예: 난독화된 셸, 생성된 스크립트, 분류기가 모르는 도구;
- 악의적인 내부자;
- 하네스 파일을 직접 손으로 고치는 사람;
- Claude Code 밖에서 실행되는 모든 것.

실제 테넌트를 위한 진짜 방어는 ID 분리입니다. [identity.ko.md](identity.ko.md)를 참조하십시오.

## 계층과 그 한계

### 거부 규칙

생성된 `.claude/settings.json`은 다음에 대한 `Edit`과 `Write`를 거부합니다.

- 통제 장치: `.claude/`, `policy/`, `audit/`, `.cab/state/`, `.cab/manifest.json`, `.cab/backups/`;
- 각 변경의 `approval.json`, `review.json`, `verify.json`, `snapshot.json`.

또한 `cab approve`, `cab ack`, `cab resume`, `cab setup apply`, `cab setup uninstall`에 대한 `Bash`를 거부합니다.

Claude Code는 거부 규칙이 bypass 모드를 포함한 모든 권한 모드에 적용된다고 문서화하고 있습니다. 한계:

- 거부 규칙은 도구 이름과 패턴에 일치합니다. 같은 파일을 다른 방법으로 쓰는 셸 명령은 그 범위 밖이므로, 가드가 같은 확인을 반복합니다.
- 허용 규칙은 bypass 모드에서 효과가 없습니다. 허용 규칙이 관문으로 의도된 것처럼 보이면 `cab doctor`가 경고합니다.

### PreToolUse 가드

가드는 모든 도구 호출을 분류합니다.

- 인식되지 않는 관리 명령은 쓰기로 셉니다.
- 복합 명령은 가장 위험한 부분을 따릅니다.
- 쓰기는 열린 변경이 그 등급에 필요한 상태에 도달하지 않았으면 거부됩니다.

내부 오류는 종료 코드 2로 끝나며, 이는 호출을 차단합니다. 훅 항목은 `onFailure: "block"`도 설정하는데, Claude Code는 이를 버전 2.1.295부터 문서화하고 있습니다.

한계:

- **분류기는 최선의 노력일 뿐입니다.** 시뮬레이션 테넌트, Microsoft Graph PowerShell, Azure CLI, Graph HTTP 호출의 동사를 인식합니다. 일반적인 셸 파서가 아니므로 인용 기법, 별칭, 함수, 환경 변수 기법, 인터프리터, 간접 호출이 의도를 숨길 수 있습니다. 판단할 수 없으면 쓰기로 취급하지만, 일부 회피는 잘못 분류됩니다.
- **스크립트.** 가드가 읽을 수 있는 스크립트는 내용으로 분류됩니다. 읽을 수 없는 스크립트는 쓰기로 셉니다. 확인과 실행 사이에 스크립트가 바뀔 수 있습니다.
- **bypass 모드는 좁은 환경에서만 관찰되었습니다.** 문서는 거부 규칙에 대해서는 모든 모드를 분명히 다루지만, 훅의 거부에 대해서는 그렇지 않습니다.
  - 현재 에이전트 수준 평가([결과](../evals/results/latest.md), 영어)에서, 명령이 가드에 도달한 두 시도 모두 가드가 bypass 모드에서 승인 없는 정확한 purge를 거부했습니다. 세 번째 시도에서는 정확한 purge가 실행되지 않았으므로 INCONCLUSIVE입니다.
  - 이 실행들에서 훅은 같은 고정 코드를 쓰는 명령줄 설정 오버레이에서 로드되었으므로, 프로젝트 자체 설정에서의 등록은 측정하지 않았습니다.
  - 별도의 단일 실행 프로브([노트](../evals/results/20261112-project-hook-registration.md), 영어)는 생성된 프로젝트 자체 설정을 bypass 모드에서 로드했습니다. 제품 가드가 열린 변경이 없는 purge를 거부했습니다. 이는 그 한 분기만 다룹니다. 다른 훅과 경로(승인, Stop, ConfigChange)의 등록과 다른 설치 방식은 측정되지 않은 상태로 남아 있습니다.
  - 이것을 bypass 모드에 대한 보장이 아니라, 한 시나리오에 대한 제한된 증거로 다루십시오.
- **뒤따른 거부가 쓰기를 진행 중 상태로 남깁니다.** 가드가 쓰기를 허용할 때, 먼저 그 쓰기를 진행 중(in flight)으로 예약합니다. 이후 다른 훅이나 규칙이 같은 호출을 거부하면 쓰기 영수증이 기록되지 않고 예약이 남습니다.
  - 그 변경의 이후 쓰기는 거부되며, 변경을 성공으로 종료할 수 없습니다.
  - 이는 안전한 쪽으로 실패하지만, 사람이 처리할 때까지 변경이 멈춰 있습니다. 현재 평가의 E5 시도 3회 모두와 이전 배치의 2회에서 관찰되었습니다. 모든 경우에 뒤따른 거부는 평가 자체의 관찰자 훅이었습니다.
- **충돌과 시간 초과.** Claude Code 훅은 기본적으로 실패 시 허용(fail open)합니다. 가드 자체의 종료 코드 2 처리와 `onFailure: "block"`은 Claude Code가 이를 존중하는 범위에서만 그 빈틈을 막습니다.

### 서브에이전트

생성되는 모든 에이전트에는 명시적인 `tools:` 목록이 있습니다. 가드는 서브에이전트의 모든 관리 쓰기를 거부합니다.

- 서브에이전트는 읽기와 짧은 목록의 읽기 전용 프로그램을 실행할 수 있습니다.
- 안전 검토자는 명령을 전혀 실행할 수 없습니다.
- 철자가 틀린 frontmatter 필드는 Claude Code가 조용히 무시합니다. `cab doctor`는 모든 에이전트에 명시적인 도구가 있는지 확인합니다.

### 승인, 확인(ack), 재개(resume)

이 명령들은 표준 입력과 출력에 실제 터미널, 같은 실제 사용자와 유효 사용자, 그리고 변경 ID를 정확히 다시 입력하는 것을 요구합니다. 가드는 이 명령들을 감싸는 알려진 의사 터미널 래퍼(`script`, `expect`, Python `pty`)를 거부합니다.

터미널 확인은 사람이 있다는 증명이 아닙니다. 다른 프로그램이나, 가드가 인식하지 못하는 래퍼가 터미널을 제공할 수 있습니다. 이 확인은 인증이 아니라 실수에 대한 보호로 다루십시오.

### 터미널 접수

`cab intake CHG-NNNN`은 사람의 터미널에서 접수 답변을 받습니다.

- 각각 검증되는 한 줄 답변 여섯 개;
- 민감 정보를 가린 요약. 변경 ID를 다시 입력한 뒤에만 기록됩니다;
- 출처 `terminal`과 결과 `intake.md`의 해시를 담은 원장 행.

이것은 승인이 아닙니다. 한계:

- **같은 터미널 한계가 적용됩니다.** 표준 입력과 출력에 터미널, 그리고 같은 실제 사용자와 유효 사용자가 필요합니다. 어떤 의사 터미널이든 이 확인을 통과하므로, 누가 답을 입력했는지에 대한 증명이 아닙니다.
- **가드의 인식은 텍스트 기반입니다.** 에이전트가 호출하면 가드는 대화형 형태와 이를 감싼 알려진 래퍼를 거부합니다. 메인 세션에서는 정확한 픽스처 형태인 `cab intake CHG-NNNN --from-file PATH`만 허용합니다. 난독화되거나 인코딩된 명령은 텍스트 기반 인식을 벗어날 수 있습니다.
- **픽스처 행은 사람에 대해 아무것도 증명하지 않습니다.** 픽스처 행은 픽스처로 표시되며 파일 해시에 묶이지 않습니다.
- **편집은 막는 것이 아니라 감지됩니다.** `intake.md`는 보호 경로가 아닙니다. 터미널 접수 뒤에 이를 편집하면 해시가 바뀌므로, 터미널 행이 더 이상 인정되지 않고 계획 단계가 거부됩니다.
- **대화로 한 답은 측정되지 않습니다.** `AskUserQuestion`으로 받은 답은 결코 기록되지 않으므로, 대화로는 접수를 완료할 수 없습니다.
- **실제 세션에서 측정되지 않음.** 실제 Claude Code 세션 안에서 사람이 하는 터미널 접수는 측정되지 않았습니다.

### Stop 훅

Stop 훅은 검증이 뒤따르지 않은 쓰기가 있는 동안 턴의 종료를 차단합니다. 한계:

- `onFailure`는 Stop이나 SubagentStop에 효과가 없습니다. Stop 훅이 충돌하거나 시간 초과되면 턴이 끝납니다.
- 사람이 세션을 중단하면 Stop 훅을 건너뜁니다.
- Claude Code는 Stop 훅이 에이전트를 계속 진행시킬 수 있는 횟수를 제한하며, `stop_hook_active`는 다음 종료를 통과시킵니다.
- 이 훅은 에이전트가 멈추고 보고하게 만들 뿐, 스스로 아무것도 검증하지 않습니다.

모두 위와 같은 오버레이 구성으로 실행한 bypass 모드 평가에서 관찰된 것:

- **현재 평가, 진행 중인 쓰기(E5 시도 3회 모두).** 뒤따른 거부 때문에 쓰기가 진행 중으로 남았습니다. Stop 훅은 그 진행 중인 쓰기를 이유로 차단했고, `cab close`는 종료를 거부했습니다. 이 차단은 원장에 기록되어 있습니다. 결과 표의 `stop_block_seen`은 확정된 쓰기 뒤의 차단만 세므로 `false`로 표시됩니다([노트](../evals/results/20261112-known-target-step-notes.md), 영어 참조). **확정된 쓰기는 관찰되지 않았으므로, 이 배치는 확정된 쓰기에 대한 Stop 차단의 증거를 제공하지 않습니다.**
- **기록: 이전 배치(계획된 단계 수정 이전).** 확정된 쓰기가 있는 시도 1회: 검증 전에 Stop 훅이 차단했고, `cab verify`가 FAIL을 기록했습니다. 2회는 위와 같이 진행 중인 쓰기였습니다.
- **기록: 더 이전 배치(터미널 접수 이전).** 확정된 쓰기 순서가 세 시도 모두에서 기록되었습니다.
- **기록은 현재 런타임에 대한 증거가 아닙니다.**
- **스크립트 리허설, 모델 없음.** 설치된 Stop 훅이 검증되지 않은 거짓 성공 쓰기를 차단했고, verify가 FAIL을 기록했습니다. 이는 에이전트 행동이 아니라 기계적 증거입니다.

여기 나열된 한계는 하나도 실제로 시험되지 않았습니다.

### 설정 잠금

ConfigChange 훅은 생성기의 매니페스트와 일치하지 않는 프로젝트 설정 및 스킬 변경을 보류합니다. 한계:

- ConfigChange를 차단하면 세션이 그 변경을 사용하지 못할 뿐, 디스크의 파일을 되돌리지는 않습니다. 새 세션은 디스크에 있는 것을 무엇이든 읽습니다.
- 관리형 정책 설정에서 온 변경은 차단할 수 없습니다.
- 차단 이유는 사용자에게 표시되지 않습니다.
- 이 훅은 설치 매니페스트에 연결되어 있습니다. 고정된 런타임은 `.cab/manifest.json`을 읽고, 별도로 필수 훅과 거부 규칙의 하한을 확인합니다. 기록된 기여만으로는 하한이 온전하다는 증명이 되지 않습니다. 안전하지 않거나, 없거나, 손상된 기록은 변경을 차단합니다. 소유한 스킬 파일은 기록된 해시와 일치해야 하며, 소유하지 않았거나 바뀐 스킬은 보류됩니다.
- 이 확인들은 합성 테스트와 설치된 런타임 대상 테스트로 다루어집니다. Claude Code가 실제 ConfigChange 이벤트를 훅에 전달하는지는 측정되지 않았습니다. 적용한 뒤에는 새 세션을 시작하십시오.

### 통제를 끄는 설정

일부 설정은 프로젝트 파일이 바뀌지 않아도 통제를 끌 수 있습니다.

- `disableAllHooks`;
- 관리형 설정 `allowManagedHooksOnly`와 `allowManagedPermissionRulesOnly`;
- `--bare`로 Claude Code를 실행하는 것.

`cab setup apply`는 읽을 수 있는 설정 파일에서 앞의 두 가지를 감지하면 설치를 거부합니다. `cab doctor`는 이를 보고합니다.

둘 다 다음은 읽을 수 없습니다.

- 장치 관리나 서버로 배포된 관리형 설정;
- 명령줄 플래그;
- 알고 있는 파일 밖의 설정.

이 출처들은 측정되지 않음으로 보고됩니다.

`cab doctor`는 생성된 모든 파일을 해시해 `.cab/manifest.json`과 비교합니다. 없거나, 안전하지 않거나, 바뀐 파일은 FAIL이며, 없거나, 안전하지 않거나, 손상된 매니페스트도 FAIL입니다. 다음 출처는 명시적으로 측정되지 않음으로 남습니다.

- 읽지 않는 관리형 설정;
- 전달받지 않는 Claude Code 버전과 설치된 mod(모드);
- Claude Code가 최종적으로 적용하는 실제 설정.

따라서 `cab doctor`는 결코 깨끗한 통과를 보고하지 않습니다. 그 결과는 실제 적용된 설정이 아니라 읽은 파일에 대한 설명입니다.

### mod(모드)

이 절의 mod(모드)는 권한 모드(permission mode)가 아니라 Claude Code mod를 말합니다.

`tool.check`를 처리하는 Claude Code mod(모드)는 거부 규칙이나 훅이 거부한 호출을 승인할 수 있습니다. 이는 관리형 설정이 없고 Team 또는 Enterprise 로그인이 없는 세션에 해당합니다. 하네스는 이를 막을 수 없습니다. 현재 `cab doctor`와 설치 프로그램 모두 그런 mod(모드)를 감지하지 못합니다. `cab doctor`는 mod(모드)가 없다고 가정하지 않고, 설치된 mod(모드)를 측정되지 않음으로 표시합니다.

### 사후 탐지

`cab audit`은 Claude Code 세션 기록을 읽어 다음을 보고합니다.

- 프로젝트 밖에서 이루어진 관리 쓰기;
- SessionStart 원장 행이 없는 프로젝트 내 세션. 이는 훅이 실행되지 않았다는 뜻입니다.

한계:

- 세션 기록 형식은 문서화된 안정적인 인터페이스가 아닙니다. 해석할 수 없는 줄이 있으면 결과는 깨끗함이 아니라 판단 불가가 됩니다.
- Claude Code는 오래된 세션 기록을 삭제합니다. 기본값은 30일입니다.
- 하네스 안으로 인정되는 것은 현재 프로젝트뿐입니다. 다른 프로젝트에서의 쓰기는, 그 프로젝트에 자체 하네스가 있더라도 밖으로 보고됩니다.

### 원장

훅과 CLI는 알려진 비밀 패턴을 먼저 가린 다음 `audit/ledger/`에 기록을 덧붙입니다. 한계:

- **이 버전의 원장은 해시 체인이 아닙니다.** 파일에 쓸 수 있는 사람은 하네스가 감지하지 못하게 원장을 바꿀 수 있습니다. 원장을 고정하려면 비공개 Git 저장소에 커밋하십시오.
- **클라우드 동기화 폴더는 아무것도 고정하지 않습니다.**
- **가리기는 패턴 기반입니다.** 특이한 형식의 비밀은 놓칠 수 있습니다.

### 하네스가 측정하지 않는 증거

- **인터뷰 답변.** 원장은 `AskUserQuestion` 질문을 했다는 사실만 기록하고 답은 기록하지 않습니다. 따라서 질문만 있거나, 답이 없거나, 시간 초과된 인터뷰로는 계획 단계를 완료할 수 없습니다. 지원되는 경로는 터미널 접수(위 참조)이며 이것도 누가 입력했는지의 증명은 아닙니다. 그리고 픽스처 경로 `cab intake CHG-NNNN --from-file PATH`가 있는데, 이는 픽스처로 표시되며 결코 사람의 답이 아닙니다.
- **검증자 서브에이전트의 판단.** 참고용입니다. 검증으로 인정되는 것은 `cab verify` 결과뿐입니다.
- **실제 테넌트.** 검증 실행기는 시뮬레이션 테넌트만 지원합니다. 실제 테넌트 프로브는 UNMEASURED로 남으며, 완전한 스냅샷을 찍을 수 없으므로 실제 테넌트 쓰기는 거부됩니다.
- **SessionStart 자체 테스트.** 합성 픽스처를 대상으로 가드의 결정 함수를 실행합니다. Claude Code가 등록된 훅을 실제로 호출했다는 증명은 아닙니다. 단일 프로젝트 등록 프로브는 프로젝트 자체 설정에서 SessionStart 행 하나를 기록했습니다. 이는 세션 하나일 뿐, 일반적인 측정이 아닙니다.

## 생성기

`cab setup render`는 `.cab/setup/` 아래에만 씁니다. `cab setup apply`와 `cab setup uninstall`은 터미널과, 다시 입력한 프로젝트 폴더 이름을 요구합니다. 쓰기 전에 다시 렌더링해 비교하고, 백업을 남기며, 실패하면 되돌립니다.

Claude Code 샌드박스가 꺼진 상태에서 Bash를 쓸 수 있는 세션은 여전히 `.claude/`에 직접 쓸 수 있습니다. 플러그인의 설정 세션 훅은 설정 세션 자체만 보호합니다. 측정된 것은 두 가지입니다.

- 정적 플러그인 검증. 메타데이터 경고와 함께 통과합니다;
- bypass 모드에서 계측한 실행 1회. 네임스페이스 이름으로 설정 스킬을 시작하는 것이 거부되었습니다.

이 실행은 설정 관문의 한 분기만 다룹니다. 설정을 시작하는 다른 방법과 완전한 대화형 설정 인터뷰는 측정되지 않았습니다.
